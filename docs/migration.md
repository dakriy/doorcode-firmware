# Moving boards from the standard partition table

Boards that run firmware built for ESP-IDF's standard two-OTA partition
table cannot take this firmware in one update. That table has three app
slots of 1 MB (`factory` at 0x10000, `ota_0` at 0x110000, `ota_1` at
0x210000), and this firmware's image is larger than 1 MB. Its own table
(`firmware/partitions.csv`) has two larger slots instead: `ota_0` of 2 MB
at 0x10000 and `ota_1` of 1984 KB at 0x210000. `nvs`, `otadata`, and
`phy_init` sit at the same places in both tables, and both start `ota_1`
at 0x210000, so a board can move from one table to the other in place.

It takes two updates: a small stepping-stone image that fits the old slots
and rewrites the partition table, then the full image through the normal
update path.

## 1. Build the stepping-stone image

    scripts/firmware-release.sh --migrate 2.0.0-migrate /path/outside/the/repo/release-key.pem

This is the release script of `release.md` with three differences:

- It builds the `migrate` variant of the firmware (`cargo build --profile
  migrate --features migrate` with `firmware/sdkconfig.migrate` on top of
  the usual sdkconfig; `make firmware-build-migrate` builds it alone).
- It requires `firmware/provisioning.json` and embeds it. The boards it is
  meant for keep nothing in NVS that this firmware reads, so the embedded
  defaults are their broker, enrollment account, Wi-Fi network, and
  starting configuration. The image therefore carries those secrets; give
  it only to the previous update server.
- The version must end in `-migrate`, so the doorcode server never takes
  it for a release to roll out, and the signed image must fit the old 1 MB
  slots. The script refuses either otherwise. It writes
  `dist/doorcode-firmware-2.0.0-migrate.bin`.

The image is signed with the same key and in the same format as every
release (`firmware-signing.md`), which is what boards of the previous
firmware check before they install an update.

To fit 1 MB the stepping-stone image leaves out everything a board does
not need to get to the next step:

- No keypad, strike, or door sensor driver. The strike output is driven
  low (locked) at start and stays low; `open` commands do nothing, and the
  door reads as closed. The door does not open by code while a board runs
  this image, which is minutes for each board.
- No Mesh-Lite: the plain Wi-Fi station joins the access point, whatever
  the configuration says about the mesh.
- IPv4 only: the broker and the download server must be reachable over
  IPv4.
- TLS 1.2 client only, with ECDHE-ECDSA key exchange, AES-GCM, SHA-256,
  and the P-256 curve. The broker's and the device download address's
  certificates, and the CA they chain to, must be ECDSA P-256 signed with
  SHA-256.
- ESP-IDF and the firmware log errors only; error codes are logged by
  number, without their names; and a panic restarts the board without a
  message.

## 2. Offer it through the previous update server

Upload `dist/doorcode-firmware-2.0.0-migrate.bin` to the previous update
server, as the update for the boards to move. Each board
installs it into its next OTA slot, as it would any update: 0x110000
(`ota_0`) or 0x210000 (`ota_1`), depending on where it ran from.

## 3. What the stepping-stone image does when it starts

Before Wi-Fi, NVS, or anything else that reads the partition table, it
reads the table at 0x8000 and the flash address it runs from:

1. **Old table, running from 0x110000.** That slot is part of the new
   `ota_0`, which the next step overwrites, so the image copies its own
   1 MB slot, sector by sector, to 0x210000, has ESP-IDF check the copy
   and set that slot to boot, and restarts. It runs from 0x210000 next.
2. **Old table, running from 0x210000.** It erases the table's sector at
   0x8000, writes the new table (the bytes ESP-IDF's `gen_esp32part.py`
   makes from `partitions.csv`, MD5 entry included, generated by the
   build), and reads it back; it tries up to three times until the two
   match, then has ESP-IDF read the table again and goes on. `otadata`
   still names the second OTA slot, which is the new `ota_1`, so the
   bootloader keeps booting this image.
3. **New table.** It goes on.
4. **Any other table.** It logs an error, changes nothing, and goes on.

It then runs as a door without a keypad: it joins the provisioned Wi-Fi
network, enrolls, and connects to the broker. Once it has connected it
marks itself valid, as every update does (`release.md`), and reports its
version, `2.0.0-migrate`.

## 4. Roll out the full image from the doorcode server

Upload the full image to the doorcode server and make it the target
version for those doors, as in `release.md`. The server sees each door
report a version other than its target and sends an update. The door
installs it into the next OTA slot after the one it runs from, which is
the new `ota_0` (2 MB at 0x10000), boots it, and the full firmware marks
itself valid once it connects.

## Risks, and testing on a spare board first

- The table rewrite erases and writes one flash sector. A power cut in
  the few milliseconds between the erase and the end of the write leaves
  a board without a partition table, which then needs flashing over USB.
- Copying to 0x210000 overwrites what the old `ota_1` held, which may be
  the image the bootloader would roll back to. Until the stepping-stone
  image has connected and marked itself valid, a reset sends the board
  back to whatever image the bootloader finds next, which depends on
  where the previous firmware ran from.
- Neither step has a way back to the old partition table over the air.

Run the whole path on a spare board that runs the previous firmware, from
the previous update server through to the full image reporting its version,
before offering the stepping-stone image to any installed door. Keep that
board on the bench for each new stepping-stone build.
